# Сколько стоит страж

Одни и те же Java-нагрузки гоняются без гварда и через гвард, результат — на сколько процентов
медленнее с гвардом.

```
python tests/perf/bench.py --guard <MebetGuard> --java <JAVA_HOME>
                           [--reps 3] [--warmup 3] [--measure 10] [--only cpu_hash,threads]
                           [--json out.json] [--markdown out.md]
```

Как меряется:

- каждая нагрузка — отдельная JVM: прогрев 3 с (JIT), затем окно замера **не меньше 10 с**;
  результат — среднее время раунда в окне, вместе с паузами GC, как в настоящей игре;
- режимы чередуются (без · с · с · без …), чтобы прогрев процессора и соседи по машине
  били по обоим одинаково; значение режима — медиана по повторам;
- разница меньше разброса между повторами помечается «в пределах шума»;
- запуск процесса меряется снаружи: полное время процесса, который сразу выходит;
- страж при выходе печатает, сколько времени ушло на каждый его модуль, — это отдельная таблица
  в отчёте («на что тратит время сам страж»).

Что нагружает каждая нагрузка (и что из стража она задевает):

| нагрузка | раунд | что из стража задевает |
|---|---|---|
| `cpu_hash`, `cpu_sort`, `cpu_math` | SHA-256 192 МБ, сортировка 2 млн, мандельброт | ничего — контроль, здесь должно быть ≈ 0 % |
| `alloc_young` | 32 млн короткоживущих объектов | молодой GC |
| `alloc_huge` | 256 массивов по 8 МБ | огромные объекты, коммит кучи — хуки памяти |
| `threads` | 4000 потоков: старт и выход | проверка потоков и DACL на каждый новый поток |
| `class_load` | 4000 классов в новых загрузчиках | JVMTI-часть стража |
| `jni_deflate` | zip-сжатие 30 × 256 КБ | JNI |
| `game_tick` | 360 игровых тиков: физика, сетка, мусор, параллельно | всё понемногу — «как игра» |
| `frame_pacing` | игровой цикл 144 FPS 30 с: тик + отрисовка 1280×720 в кадровый буфер + мусор | плавность: p99 / p99.9 / максимум кадра и кадры вне бюджета — так видны фризы от периодических проверок стража (раз в 5 с) |
| `native_alloc` (Java 22+) | 1000 нативных блоков по 1 МБ | `VirtualAlloc`/`VirtualFree` — прямо через хуки |
| `file_mmap` (Java 22+) | 2000 отображений файла по 4 МБ | хуки секций |
| `ffm_downcall` (Java 22+) | 30 млн нативных вызовов через FFM | ничего — контроль |

В CI это джобы `perf windows/linux/macos <arch>`: таблица — в сводке прогона, JSON — в артефакте.
В `ci-ok` они не входят: это отчёт, а не проверка. Меряется dev-сборка: слои защиты в рантайме у
неё те же, что у prod (выключены только проверки ВМ и dev-режима при старте).

## Настоящий клиент

`tests/perf/minecraft/run.py` гоняет сам клиент (профиль modern: Forge 1.7.10, LWJGL 3, Angelica) без
гварда и через гвард по очереди. Мод-бенчмарк (`MebetBenchMod.java`) сам входит в мир (без
синтетического ввода — страж его отбрасывает), 20 с прогрева, 60 с замера с камерой, которая делает
полный круг за 6 с, пишет FPS, 1 % low, p50/p99/p99.9/максимум кадра и время загрузки и закрывает
игру. Работает на копии папки клиента, мир восстанавливается перед каждым прогоном. Authlib клиента —
сборка лаунчера и без лаунчера в процессе не стартует, поэтому для замера первой в classpath идёт
заглушка его доступа к лаунчеру (`authlib-stub/`: профили не находятся, скин по умолчанию) — одна и та
же в обоих режимах.

## Результаты

**2026-11-26, Windows 11 x64, RTX 5080, Liberica 25, dev-сборка стража `a71bfa9`.**

Нагрузки `bench.py` (окно ≥ 10 с, медиана по 3–5 повторам): чистые вычисления, GC, огромные массивы,
JNI, игровой тик, хуки памяти (`native_alloc`, `file_mmap`), FFM-вызовы — разница в пределах шума
(±0–4 %); единственная разница больше шума — `class_load` **+6,9 %** (классы, определяемые в
рантайме). Плавность 144 FPS за 30 с: p99 1,19 → 1,20 мс, максимум 1,98 → 2,15 мс, кадров вне
бюджета 0 → 0. Запуск процесса: **+222 мс** (проверка подписей модулей ≈ 108 мс, стартовая
самопроверка ≈ 40 мс).

Настоящий клиент (1280×720, VSync выкл., FPS без ограничения, по 3 прогона):

| | без гварда | с гвардом | разница |
|---|---:|---:|---:|
| средний FPS | 1043,9 | 1049,3 | +0,5 % (шум между прогонами ±5 %) |
| 1 % low FPS | 492,1 | 492,4 | +0,1 % |
| кадр p99 / p99.9 / максимум, мс | 1,73 / 2,32 / 13,1 | 1,70 / 2,24 / 13,6 | в пределах шума |
| до главного меню / до мира | 35,5 с / 37,0 с | 35,8 с / 37,3 с | +0,3 с |

Сам страж за прогон: проверка подписей 103 модулей ≈ 1,2 с (в основном при старте, частично
параллельно загрузке), обход памяти ≈ 24 мс раз в 5 с, обход потоков ≈ 0,6 мс раз в 5 с — всё в
своём потоке, на кадры не влияет; разовый отчёт о драйверах — 1,8–5 с (тоже в своём потоке).

**2026-11-27, та же машина: Ex-хуки (`NtCreateSectionEx`, `NtMapViewOfSectionEx`,
`NtUnmapViewOfSectionEx`, `NtAllocateVirtualMemoryEx`) — сборка `bcca2e9` против `d30a491` без них.**
