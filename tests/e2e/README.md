# End-to-end layer tests

Каждый сценарий гоняется **дважды** — без гварда и через гвард — и это два отдельных теста.
Сценарии двух видов: **атака** (что делает чит) и **легитимное действие** (что делает сама игра).

Атака:

- **без гварда** — целевая JVM (`MebetTarget`) запускается обычным `java`. Атака **должна
  сработать**: её маркер появляется в выводе, приложение продолжает работать.
- **через гвард** — та же JVM запускается обёрткой (`MebetGuard.exe` / `MebetGuard`), ровно
  как настоящий клиент. Атака **должна быть заблокирована**: гвард закрывает процесс с кодом
  этого слоя (`config/exit_codes.json`) или молча нейтрализует атаку, а приложение живёт.

Слой засчитан, только если **и** без гварда атака воспроизвелась, **и** через гвард она больше
не проходит. Это и есть пруф «было уязвимо → стало закрыто» через наш исполняемый файл. Где
атака может тихо не состояться (например, не получилось открыть поток стража), через гвард
дополнительно проверяется, что атака **была проведена** (строка «заморожено N≥1 потоков»):
иначе тест падает как недоказательный. «Закрыт» засчитывается по коду выхода; строка
`[Mebet] closed` без кода — только если приложение действительно остановилось. Атака изнутри
игры засчитывается, только если игра до неё дошла (строка `TARGET action:`): страж, который
по ошибке отверг библиотеку самой JVM, выходит с тем же кодом ещё до `main()`.

Легитимное действие (обычный запуск, тысячи потоков, JIT, библиотека самой Java, обычный
нативный вызов через FFM) должно работать **в обоих** прогонах: страж не должен мешать игре.

Один тест на каждый сценарий (pytest — видно каждый сценарий отдельно):

```
pytest tests/e2e -v --guard <MebetGuard> --java <JAVA_HOME> [--untrusted-native <lib>]
```

Сценарий `dev_mode` (prod-сборка на машине в dev-режиме закрывается с 203) в обычном прогоне
пропускается: с любой другой сборкой или машиной он пройти не может. Его включает
`--expect-dev-mode` — так его запускает CI на prod-сборке.

```
tests/e2e/test_layers.py::test_layer[module_trust_load-baseline]  PASSED   без гварда: атака сработала
tests/e2e/test_layers.py::test_layer[module_trust_load-guarded]   PASSED   через гвард: закрыт, код 210
tests/e2e/test_layers.py::test_layer[thread_churn-baseline]       PASSED   работает
tests/e2e/test_layers.py::test_layer[thread_churn-guarded]        PASSED   работает, страж не мешает
```

Быстрая таблица без зависимостей (та же логика, одна строка на сценарий):

```
python tests/e2e/run.py --guard <MebetGuard> --java <JAVA_HOME> [--only id,id]
                        [--untrusted-native <lib>] [--work <dir>] [--json <out>]
```

Сценарии описаны в `harness.py` (`SCENARIOS`); добавить слой = добавить одну запись, тест на
него появляется сам. Оракул разделён на «без гварда сработало» и «через гвард заблокировано»,
поэтому упавший тест прямо говорит, какая половина сломалась.

Раннер сам собирает цель (`target/MebetTarget.java`), агент-маркер (`attacks/MebetMarkerAgent.java`
→ `mebet-marker.jar`) и неподписанный натив (`attacks/native/mebet_fake_cheat.c`, компилятором
`clang`/`cl`/`gcc`; если его нет — сценарии с нативом пропускаются или натив передаётся через
`--untrusted-native`). Выход ненулевой, если хоть один слой не прошёл.

## В GitHub Actions

Один workflow `.github/workflows/ci.yml`, четыре стадии:

```
1. сборка   Matrix: build-windows-binaries   windows x64 prod · x64 dev · x86 prod · x86 dev · arm64 prod · arm64 dev
            Matrix: build-linux-binaries     linux x64 prod · x64 dev · arm64 prod · arm64 dev
            Matrix: build-macos-binaries     macos x64 prod · x64 dev · arm64 prod · arm64 dev
2. e2e      (каждая — после сборки своей ОС; джоб на архитектуру × фичу)
            Matrix: e2e-windows   x64 · x86 · arm64  ×  каждый сценарий из harness.SCENARIOS для Windows
                                  (на x86 — без сценариев FFM)
                                  + x64 × paths-cyrillic · paths-specials · paths-beyond
            Matrix: e2e-linux     x64 · arm64  ×  clean_launch · thread_churn · jit_hot · ffm_benign ·
                                  env_hardening_jto · env_hardening_jdk · jvm_agents_javaagent ·
                                  jvm_agents_agentpath
                                  + x64 × paths-cyrillic · paths-specials · paths-beyond
            Matrix: e2e-macos     x64 · arm64  ×  то же, что linux (paths-* — на arm64)
3. ci-ok    зависит только от трёх e2e; красный, если любая упала, отменена или пропущена
            (пропущена = упала её сборка) — его требует правило ветки master
4. sign     только на тегах v* (на pull request всегда skipped)
```

Каждая сборка — отдельный джоб матрицы со своей галочкой и своим артефактом
`bin-<os>-<arch>-<variant>`; в саммари прогона у каждой раскрывающийся блок: чем и как собрано,
файлы, размеры, sha256. **prod** = `release` (все модули включены), **dev** = `devtest`
(выключены модули `virtual_machine`, `linux_wsl` и `dev_mode` — гвард стартует на ВМ и на
dev-режимном раннере).

Каждая архитектура — на своём железе: Windows x64 и x86 на `windows-2022` (x86 — 32-битный
процесс под WOW64, чистой 32-битной Windows у GitHub нет), Windows arm64 на `windows-11-arm`,
Linux arm64 на `ubuntu-24.04-arm`, Mac Intel на `macos-15-intel`, Mac Apple Silicon на `macos-15`.
Для x86 — 32-битная Java 21 от BellSoft: 32-битной Java 25 под Windows не выпускает ни один
вендор. В CI тесты идут с `--no-skip`: сценарий, который здесь не может выполниться (например,
нет компилятора для натива), валит джоб, а не пропускается молча.

e2e на Windows идёт на **dev**-сборке, кроме фичи `dev_mode`: она берёт **prod**-сборку и проверяет,
что та закрывается кодом **203** — раннеры GitHub грузятся с test-signing. Java для Windows-e2e —
Liberica (BellSoft): гвард доверяет издателю Java игры, DLL другой Java закрыл бы как недоверенные.

Что тесты не фейковые: подставь вместо гварда обычную `java` — все такие тесты падают (атака
проходит, защиты нет). Проверено.

## Неудобные пути (`--paths`)

Игроки держат игру в `C:\Users\Иван\AppData\Roaming\.politcubes` и `D:\Игры\Мой клиент (копия) & моды`.
`--paths <вариант>` копирует страж (два его файла) и JDK (настоящая копия: junction спрятал бы имя)
и кладёт рабочую папку — папку клиента: текущий каталог, `-cp`, агент-маркер, неподписанный натив —
в папки с такими именами; дальше выбранные сценарии идут как обычно, без гварда и через гвард
(`paths.py`):

| Вариант | Что в именах |
|---|---|
| `cyrillic` | `Игра Тест` |
| `specials` | пробелы и `& ( ) [ ] ! % ^ ' ; , = # + ~`, на Linux/macOS ещё `$ \ * ?`; на Windows папка стража такой длины, что `MebetGuard.dll` — 254 символа |
| `beyond` | символы вне кодовой страницы ANSI Windows: эмодзи, иероглифы, кириллица, `Ł` (Windows молча делает из неё `L`) |

В папке стража — всё сразу: обычная java её не видит, страж обязан работать из неё всегда
(на macOS без `=`: JVM режет `-agentpath:<путь>=<опции>` по нему, страж закрывается с
`unsupported_path`, 226). В папке Java и папке клиента — только то, что принимает сама java на этой
машине, иначе прогон без гварда падает и ничего не доказывает: на Windows — буквы кодовой
страницы ANSI (раннеры CI — 1252: кириллица туда не входит), без `;` (разделитель путей) и `=`
(java режет по нему `-javaagent:<jar>=<опции>`), без `:` на Linux/macOS, без `\` в папке клиента на
Linux/macOS (экранирование в `JDK_JAVA_OPTIONS`), эмодзи — только у стража.

Папки, которые кодовая страница ANSI не выражает вовсе, на Windows проверяет `test_paths.py`
(`-k beyond_code_page`, с `--paths cyrillic` или `beyond`): обычная java из такой папки Java не
стартует; страж запускает игру через имя 8.3 или, если его нет, закрывается с `unsupported_path`
(226) — а не висит за окном JLI «could not find java.dll», как раньше. Из такой папки клиента страж
заканчивается так же, как обычная java (её код выхода, без своего закрытия).

```
pytest tests/e2e -v -rP --paths cyrillic --guard <MebetGuard> --java <JAVA_HOME> [--work <dir>]
```

## Виды сборки

`MEBET_BUILD_KIND` (через `config/modules.json`) даёт три вида:

- **release** — все модули включены, `virtual_machine`/`linux_wsl`/`dev_mode` на «закрыть».
  Подписываемый клиентский билд.
- **test** — `virtual_machine` и `linux_wsl` выключены (можно гонять в ВМ/контейнере на стенде и
  в e2e); `dev_mode` остаётся на «закрыть». Неподписанная.
- **devtest** — то же, что `test`, плюс выключен модуль `dev_mode` (для прогона Windows-слоёв на
  dev-режимных раннерах GitHub). Неподписанная, игрокам не раздаётся.

`dev_mode` залочен на «закрыть» в `release` и `test`; выключить его может только `devtest` —
это проверяет генератор. e2e для слоёв `virtual_machine`/`linux_wsl` идёт на **release**-сборке
в настоящей ВМ (204) и в WSL2 (205).

Легитимные сценарии (страж не мешает, на всех ОС и архитектурах, где применимо): обычный
запуск, 2000 коротких Java-потоков (старт и выход потока идут через хуки — ловит падения вроде
снятого TLS у уходящего потока), горячий цикл под JIT, `System.load` библиотеки самой Java
(Windows), обычный нативный вызов через FFM (Java 22+), пауза всего процесса на 35 с и
продолжение (Windows: «Приостановить» в диспетчере — сторож потоков не должен принять это за
остановку стража), библиотеки самой Java грузятся и выгружаются 45 с подряд на нескольких
потоках (Windows, FFM: обход памяти не должен принять образ, который хук ещё записывает, за
скрытый).

Сборка Linux дополнительно проверяется `tools/ci/check-glibc.sh`: бинарники не должны требовать
glibc новее 2.28 — иначе на Debian 10 / RHEL 8 / Ubuntu 18.10 страж не запустится вовсе.

FFM-атаки (Foreign Function & Memory API, Java 22+) — это чит-мод без своей DLL: Java-код
сам зовёт `VirtualAlloc`, `SuspendThread`, `FreeLibrary`. На 32-битной Windows их нет: у 32-битной
Java нет FFM-линкера, а Java 22+ под x86 не выпускается.

Слои уровня «отчёт» (`report`) не закрывают клиент — их e2e проверяет, что событие отправлено;
это требует тестового канала GlitchTip и будет добавлено вместе с ним.

### Модель угрозы: чит внутри процесса

Читы для Minecraft почти всегда внутрипроцессные — мод или jar внутри игровой JVM, а не
внешний инжектор. Поэтому слои памяти (`module_trust`, `foreign_exec_memory`, `foreign_threads`)
проверяются как поведение чит-мода **изнутри** целевой JVM: цель сама грузит чужой натив
(`System.load`), выделяет исполняемую память, стартует чужой поток — ровно то, что делает мод.
Так проверка не зависит от отдельного инструмента-инжектора.

`module_trust` и `jvm_agents` (`-agentpath`) используют одну неподписанную натив-заглушку
(`attacks/native/mebet_fake_cheat.c`, только маркер: экспортирует `JNI_OnLoad`, `Agent_OnLoad`,
`Agent_OnAttach`) — на Linux/macOS её собирает раннер сам (`cc`/`clang`/`gcc`), в Windows-CI —
MSVC в каждом e2e-джобе (`fixtures\mebet_fake_cheat.dll`, в артефакты не выкладывается); на стенде
её собирают так же или передают готовую через `--untrusted-native`.

Внешняя инъекция из другого процесса (`CreateRemoteThread` и т.п.) закрывается DACL процесса
(`process_dacl`): его e2e проверяет, что процесс стража нельзя открыть с правами на запись
памяти и создание потока, — отдельного инструмента-инжектора для этого не нужно.

## На всех системах

- **Windows x64/x86/arm64** — полный набор слоёв (гейт `NtCreateSection`, память, потоки, DACL).
- **Linux x64/arm64, macOS** — слои старта (чужой агент, окружение, WSL, LD_PRELOAD). In-process
  детект инъекции в память на Linux/macOS в страже пока не подключён, поэтому соответствующие
  слои там помечены как Windows-only, пока это не появится.

Все слои гоняются прямо на раннерах GitHub своей ОС и архитектуры, на **dev**-сборке (`devtest`);
только `dev_mode` — на **prod**. Linux-бинарники при этом собираются в контейнере
`manylinux_2_28`, чтобы запускаться на glibc 2.28.
